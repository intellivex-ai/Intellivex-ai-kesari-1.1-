## 2026-04-15 - [Fix IDOR in api/generate-image.ts]
**Vulnerability:** Insecure Direct Object Reference (IDOR) where any authenticated user could insert image messages into any other user's chat.
**Learning:** The application was missing explicit authorization checks (resource ownership verification) on the server side when performing operations via API endpoints that accept identifiers (like `chatId`) from the client.
**Prevention:** Always verify resource ownership (e.g., query the `chats` table to match the `user_id` with the authenticated `userId`) before allowing modifications or creations on that resource.
## 2025-02-27 - [Fix IDOR in vite-api-plugin.ts messages endpoints]
**Vulnerability:** In `vite-api-plugin.ts` (the local API server), the `GET /api/messages` and `POST /api/messages` endpoints used `sbFetch` directly to query `messages` using `chat_id`. Since `sbFetch` bypasses Row Level Security (RLS) by using `SUPABASE_SERVICE_ROLE_KEY`, this created an Insecure Direct Object Reference (IDOR) / authorization bypass where any user could read or write messages to any chat ID they guessed, without their ownership of the chat being verified.
**Learning:** Endpoints that bypass RLS using service roles *must* implement their own authorization logic. You cannot rely on Supabase to filter data when using the service role key. Furthermore, the wrapper function `sbFetch` returns an array on success. When checking resource ownership, we must validate the response type explicitly (e.g. `Array.isArray(chatData)` and `chatData.length > 0`) to fail closed on error objects.
**Prevention:** Always verify resource ownership (e.g., fetching the chat record and ensuring `chat.user_id === userId`) before allowing read/write operations in endpoints that use `SUPABASE_SERVICE_ROLE_KEY`. Validate response types defensively to fail securely.
